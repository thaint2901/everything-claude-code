# Configure Everything Claude Code (ECC)

**この**リポジトリが必要とする ECC スキルとルールを決め、その候補リストをインストールします。

このスキルの成果物は**評価**です。根拠のある選択と、除外したものの理由の両方を指します。リポジトリが必要とする以上のスキルを入れることは実コストであり — インストール済みのスキルは毎セッションのコンテキストを消費します — 除外は選択と同じだけ立派な成果物です。

## 起動タイミング

- ユーザーが "configure ecc"、"install ecc"、"setup everything claude code" などと言った場合
- ここでどの ECC スキルやルールを入れる価値があるかを判断したい場合
- リポジトリが変化したため、既存の ECC インストールを再評価したい場合
- 既存の ECC インストールを検証、修正、または調整したい場合

## このスキルが行わないこと

`/project-init` はすでにプロジェクトのスタックを検出し、マニフェストからインストール計画を解決し、dry-run を実行し、承認を経てから進みます。**それらを再実装しないでください。** 呼び出して、その出力を証拠として使います。

このスキルが担うのは `/project-init` が行わない 2 点です：

1. **判断** — スタックマッピングは機械的です。「このリポジトリは Python だが Web 層がないので `fastapi-patterns` はここではノイズだ」という結論は導けません。
2. **調整** — インストール済みファイルを、このプロジェクトが実際に使う内容まで削り込むこと。

## 仕組み

3 つのフェーズをこの順で実行します。前のフェーズが次のフェーズを現実的なコストに収めるからです：

1. **バンドル単位で除外する** — テーマ別バンドルごとに安価な質問を 1 つだけ行います。落ちたバンドルは、そこに属するスキルをまとめて対象外にします。
2. **証拠で選ぶ** — 生き残ったバンドルの中に限り、リポジトリ内の具体的な信号に照らして各スキルを判断します。
3. **反証で確定する** — 提示する前に、各推奨を壊しにいきます。

3 つすべてを生き延びたスキルだけを推奨します。

## 前提条件

このスキルは起動前に Claude Code からアクセス可能である必要があります。ブートストラップには2つの方法があります：

1. **プラグイン経由**: `/plugin install ecc@ecc` — プラグインがこのスキルを自動的にロードします
2. **手動**: このスキルのみを `~/.claude/skills/configure-ecc/SKILL.md` にコピーし、"configure ecc" と言って起動します

## ステップ 0: ECC ソースの特定

ユーザーが既に持っているチェックアウトを優先します。リモートのクローンはフォールバックであり、決して既定の手段ではありません — fork では、上流をクローンするとユーザーが動かしていないコードを黙ってインストールすることになり、これは `commands/project-init.md` がすでに禁じています。

新たに推測するのではなく、このリポジトリが同梱しているリゾルバを使ってください：

```bash
# 1. Claude Code exports this when ECC runs as a plugin.
ECC_ROOT="${CLAUDE_PLUGIN_ROOT:-}"

# 2. Otherwise ask resolve-ecc-root.js, which walks
#    env var -> standard install -> known plugin roots -> plugin cache.
[ -n "$ECC_ROOT" ] || ECC_ROOT=$(node -e \
  'try{console.log(require(require("os").homedir()+"/.claude/scripts/lib/resolve-ecc-root").resolveEccRoot())}catch(e){}' \
  2>/dev/null)

# 3. Last resort: the repository the user is standing in.
[ -n "$ECC_ROOT" ] || ECC_ROOT=$(git rev-parse --show-toplevel 2>/dev/null)
```

続いて、そのツリーが本当に ECC であることを検証します。この確認は見た目以上に重要です：`git rev-parse` は*どの* git リポジトリでも成功するため、これがないと `ECC_ROOT` がユーザー自身の無関係なプロジェクトを指しかねません。しかもその誤りは、ソース検出の失敗としてではなく、数ステップ後に紛らわしい「module not found」として表面化します。

```bash
for f in scripts/install-plan.js manifests/install-modules.json skills; do
  [ -e "$ECC_ROOT/$f" ] || { echo "Not an ECC tree: $ECC_ROOT (missing $f)"; exit 1; }
done
```

すべての手段が失敗した場合は、その旨を伝えてユーザーにパスを尋ねてください。`https://github.com/affaan-m/everything-claude-code.git` のクローンは明示的な同意がある場合に限り行い、インストールが終わったらそのクローンを `rm -rf` してください。

## ステップ 1: マニフェストから候補集合を構築する

```bash
node "$ECC_ROOT/scripts/install-plan.js" --list-components --family skill --json
```

これが非ゼロで終了したり、何も出力しなかった場合は、中断してエラーを報告してください。空の候補集合のまま進めるのは、失敗するより悪い結果になります。ルックアップの失敗と、本当に何も必要としないリポジトリは、どちらも「Recommended (0)」として表示され、ユーザーにはどちらが起きたのか判別する手段がないからです。

このファイルにスキル一覧をハードコードしないでください。ここに書いた一覧はスキルが 1 つ追加された時点で古くなり、しかもハードコードされた一覧は候補集合を黙って狭めます — 候補の一部しか見えない評価は、評価ではありません。

## ステップ 2: バンドル単位で除外する

候補を 1 つずつ判断するのはコストに見合わず、その必要もありません。カタログの大半は 1 回のパスで除外できます。

`$ECC_ROOT/manifests/install-modules.json` を読みます。`id` が `skill-` で**始まらない**モジュールがテーマ別バンドルであり、それぞれの `paths` グロブが、そのバンドルの持つスキルを示します。バンドルごとに安価な質問を 1 つ — 「このリポジトリはこの領域に少しでも触れているか？」 — と問い、ファイル一覧、パッケージマニフェスト、CI 設定から答えます。

1 つの「いいえ」で、そのバンドルのスキルはすべて除外されます。評価のコストが実際に制御されるのはここです。

除外は積極的に行ってください。コストが非対称だからです。誤って除外したバンドルはユーザーからの一文の指摘で済みますが、誤って含めたバンドルは毎セッションのコンテキストを無期限に消費し続けます。

突き合わせのルールが 2 つあります：

- どのテーマ別バンドルにも属さないスキルが少数あります。生き残った集合をステップ 1 の全体一覧と突き合わせ、バンドルの掃き出しが唯一の入口にならないようにしてください。
- どのバンドルをどの証拠で除外したかを記録します。その一覧は報告に入り、「意図的に除外」の節のほとんどを占めます。

生き残ったものの、リポジトリからはまったく判断できないバンドル — ビジネス、コンテンツ、業界ドメイン — は、除外も評価もしません。それぞれ 1 つの質問としてステップ 6 に送ります。

## ステップ 3: 証拠で選ぶ

対象は、生き残ったバンドルの中にあるスキルだけです。

`/project-init --dry-run` を実行し、検出されたスタックの証拠と解決された計画を保持します。`$ECC_ROOT/config/project-stack-mappings.json` を相互参照します。これはプロジェクトの指標ファイルを ECC のスキル、ルール、フック、コマンドに対応づけたものです。カタログの一部しかカバーしていないため、ヒットは近道として扱い、ヒットしないことはどちらの方向の信号でもないと扱ってください。

そのうえで、マッピングが表現できる範囲の先を、リポジトリを読んで確かめます：

- 対応づけられたフレームワークのうち、実際に使われているものはどれで、単に推移的依存として存在するだけのものはどれか？
- そのスキルが前提とする層 — Web 層、DB 層、CI パイプライン、UI — はこのリポジトリにあるか？
- 既存の `CLAUDE.md`、`.claude/rules/`、あるいはチームの既存規約が、そのスキルの追加内容をすでにカバーしていないか？
- テストとビルドのスクリプトは、このチームの実際の進め方について何を語っているか？

すべての推奨は、反証可能な主張を伴わなければなりません — 印象ではなく、誰かが再確認できるファイルと行です。「React プロジェクトに見える」は証拠ではありません。「`package.json:14` が `react@19` に依存している」が証拠です。要点は形式を整えることではありません。誰にも確認できない主張は誰にも訂正できず、この報告は反論されるためにあるからです。そうした主張を欠く推奨は、弱い推奨ではなく除外です。

ユーザーにスタックを尋ねないでください。リポジトリが答えを持っており、尋ねること自体が評価を省いた合図になります。

生き残った各候補に、マニフェストは持っているが component レコードには載っていない 2 つの信号を付与します：

**出所** — `$ECC_ROOT/skills/<id>/SKILL.md` の `metadata.origin` を読みます。実際に使われている値には `ECC`（ファーストパーティ）、`community`、ベンダーや個人の貢献者があります。出所を一切宣言していないスキルも多く、それらは `unknown` として報告してください。出所がないものを `ECC` として既定値扱いしたくなる引力に抗ってください — そのファイルが ECC リポジトリの中にあることは、誰が書いたかについて何も語りません。ファーストパーティのスキルと単一ベンダーのドメインスキルを、同等の推奨としてユーザーに届けてはいけません。

**成熟度** — `$ECC_ROOT/manifests/install-modules.json` で当該スキルを持つモジュールの `stability` を読みます。値は `stable` と `beta` です。`beta` は推奨時に明示してください。

**レガシー — 既知の限界。** マニフェストのどこにも `deprecated` フィールドは存在せず、スキルのライフサイクル方針もありません。利用できる唯一の信号は description の自由文なので、`legacy`、`superseded`、`prefer <other-skill>` を照合し、その結果を*不完全なもの*として扱ってください。網羅的な検査であるかのように示唆せず、報告にその旨を書きます。現状これで捕捉できる唯一の事例は、`continuous-learning-v2` に置き換えられた `continuous-learning` です。

## ステップ 4: ルールを評価する

ルールは別立てで評価します。裏付けとなるデータが薄いからです。言語名をここに列挙せず、実行時に `$ECC_ROOT/rules/*/` を列挙してください。

ルールにはマニフェストの component もバンドルも `origin` も `stability` もありません — ツリー全体が 1 つのモジュールとしてインストールされます。存在しない値を推測せず、報告では該当する列を空欄のままにしてください。

一方でルールが持っているのは、このスキルの中で最も容易な証拠です：ディレクトリ名がそのまま信号になります。`rules/python/` を正当化するのは `pyproject.toml` であって、判断の産物ではありません。ステップ 3 と同じ基準 — 指標ファイルを挙げる — を適用すれば、あとは自ずと決まります。

言語ルールは共通ルールの拡張です。評価が `common` なしで言語を選んでいる場合は、その旨を伝えて追加を勧めてください。

## ステップ 5: 反証で確定する

何かを提示する前に、それを壊しにいきます。各推奨の主張を、それを生み出した推論から切り離して**単独で**取り上げ、それが間違っている理由を探してください：

- 指標ファイルは実在し、そのパスにあり、主張どおりの内容になっているか？
- その依存は実際に使われているか、宣言されているだけか？
- リポジトリはすでにこれを解決していて、そのスキルは有用ではなく冗長になっていないか？

生き延びなかったものは落とします。主張を推論から切り離すことこそが要点です。自分の議論を読み返すモデルはそれを説得力あるものと感じがちで、裏付けを探す検証パスは、正しさを足さないまま確信だけを足します。反証を探すことが、この検査を実施する価値を生みます。

すべての推奨を「当てはまりそうなものを全部選ぶ」ではなく、予算制約のあるものとして扱ってください。「このプロジェクトは Python である」は `python-patterns` を正当化しますが、Python エコシステムのすべてのスキルを正当化はしません。

これを既に計測しているスキルと組み合わせ、作り直さないでください：

- `context-budget` — スキル、ルール、エージェント、MCP サーバーにまたがるコンテキスト消費を監査
- `skill-stocktake` — インストール済みスキルとコマンドの品質を監査

すでに ECC がインストール済みのリポジトリなら、それとの差分を取ります。追加だけでなく、支える証拠が消えたスキルの削除も推奨してください。

## ステップ 6: 評価を報告する

何かをインストールする**前に**、次の構成で評価を提示します：

```text
## ECC Assessment — <repo>

### Detected evidence
- <signal at file:line> -> <what it implies>

### Recommended (N)
| Skill | Origin | Maturity | Evidence (file:line) | Why |

### Deliberately excluded (M)
| Skill / bundle | Why not |

### The repository cannot answer these
- <bundle> — <the one question to ask the user>

### Not assessed
- <anything the available data could not judge, including the legacy-detection gap>
```

除外の表は埋め草ではありません。判断が下された記録であり、次回の実行を推測のやり直しではなく差分にするものです。

ユーザーに尋ねるのは 3 番目の節にあるバンドルについてだけです — スキルごとに 1 問ではなく、バンドルごとに 1 問です。そのうえで `AskUserQuestion` で候補リストを確認します。候補集合の全体を列挙してはいけません — 収まりませんし、提示すること自体が評価する意義を損ないます。

## ステップ 7: インストールレベルの選択

`AskUserQuestion` を使用します：

```text
Question: "Where should the selected components be installed?"
Options:
  - "User-level (~/.claude/)" — "Applies to all your Claude Code projects"
  - "Project-level (.claude/)" — "Applies only to the current project"
  - "Both" — "Common/shared items user-level, project-specific items project-level"
```

ターゲットディレクトリを設定します：

- ユーザーレベル: `TARGET=~/.claude`
- プロジェクトレベル: `TARGET=.claude`（現在のプロジェクトルートからの相対）
- 両方: `TARGET_USER=~/.claude`, `TARGET_PROJECT=.claude`

```bash
mkdir -p $TARGET/skills $TARGET/rules
```

## ステップ 8: 候補リストをインストールする

承認された各スキルについて、正しいソースルートからスキルディレクトリ全体をコピーします：

```bash
# Core skills live under .agents/skills/
cp -R "$ECC_ROOT/.agents/skills/<skill-name>" "$TARGET/skills/"

# Everything else lives under skills/
cp -R "$ECC_ROOT/skills/<skill-name>" "$TARGET/skills/"
```

グロブで得たソースディレクトリを反復処理する際、末尾スラッシュ付きのソースを `cp` に直接渡してはいけません。ディレクトリのパスを宛先名として明示してください：

```bash
cp -R "${src%/}" "$TARGET/skills/$(basename "${src%/}")"
```

コピーごとに終了ステータスを確認し、失敗は直ちに表面化させてください。黙ってコピーに失敗したスキルは、そもそも選ばれなかったスキルより悪い結果になります。報告はそれをインストール済みとして主張してしまうからです。

`SKILL.md` だけでなくディレクトリ全体をコピーしてください — いくつかのスキルは `config.json`、フック、スクリプトを同梱しています（`continuous-learning`、`continuous-learning-v2`）。

評価で選ばれたルールディレクトリを、言語別レイアウトを保ったままインストールします：

```bash
cp -r "$ECC_ROOT/rules/common" "$TARGET/rules/common"
cp -r "$ECC_ROOT/rules/<language>" "$TARGET/rules/<language>"
```

## ステップ 9: インストールの検証

まず、ディスク上にあるものをステップ 6 で承認された内容と突き合わせます：

```bash
ls -la $TARGET/skills/ $TARGET/rules/
```

眺めるだけでなく、数えて差分を取ってください。承認された項目はすべて存在していなければなりません。この順序が重要なのは、空のディレクトリが以下の grep 検査では健全な状態とまったく同じに見えるからです：`grep` が何も見つけられない場合と、`grep` に検索する対象がそもそもない場合は、同じ出力になります。部分的なインストールは、問題なしではなくインストールの失敗として報告しなければなりません。

```bash
grep -rn "~/.claude/" $TARGET/skills/ $TARGET/rules/
grep -rn "../common/" $TARGET/rules/
```

**プロジェクトレベルのインストールでは**、`~/.claude/` パスへの参照を洗い出します：

- `~/.claude/settings.json` — 問題なし。設定は常にユーザーレベルです
- `~/.claude/skills/` または `~/.claude/rules/` — プロジェクトレベルでは壊れる可能性があります
- スキルが別のスキルを名前で参照 — 参照先もインストールされたか確認します

相互参照は決めつけずに導き出してください：インストール済みファイルをステップ 1 の他の候補名で grep し、ヒットしたのにインストールされていないものを報告します。`*-tdd` や `*-testing` のスキルは通常、対応する `*-patterns` のスキルを期待し、`continuous-learning-v2` はユーザーレベルの `~/.claude/homunculus/` ディレクトリを期待します — ただし、それらは実際に探して見つけてください。ここに書かれた依存関係の一覧は、ハードコードされたスキル一覧とまったく同じように古びるからです。

各問題は、ファイル、行、何が問題か、推奨される修正の形で報告します。

---

## ステップ 10: インストール済みファイルの調整

評価が具体的な変更になるのがこの段階です。`AskUserQuestion` を使用します：

```text
Question: "Tailor the installed files to this project?"
Options:
  - "Tailor skills" — "Drop sections that do not apply, fix paths for this install level"
  - "Tailor rules" — "Match coverage targets, formatters, and workflow to this repo"
  - "Tailor both" — "Full pass over everything installed"
  - "Skip" — "Keep everything as-is"
```

すべての編集は、ステップ 3 で集めた証拠 — プロジェクト実際のテストランナー、フォーマッタ、カバレッジ目標 — に基づいて行い、ユーザーにスタックを言い直させないでください。

**重要**: 変更してよいのは `$TARGET/` 配下のファイルのみです。`$ECC_ROOT/` のソースリポジトリは決して変更しないでください。

---

## ステップ 11: 判断を記録する

評価 — 選択したもの、除外したもの、それぞれの理由 — をプロジェクト内の永続的な場所に書き出し、次回の実行がゼロからではなく差分になるようにします。結論だけでなく、**実施した検査**も記録してください：どのファイルを開き、何を検索したか。それが次回の実行を、推測のやり直しではなく差分（「前回は React がなかった、今回はある」）に変えるものです。

プロジェクトが `ecc-install.json` を保持しているなら、インストール内容と整合させてください。以後 `/project-init --config ecc-install.json` で同じインストールを再現できます。

要約を出力します：インストールレベルとパス、何を入れたか、何を除外しその理由は何か、検出および修正した検証上の問題、適用した調整。

## 例

**フロントエンドを持たない Django API。** `pyproject.toml` と `manage.py` があり、`package.json` はありません。フロントエンド、JVM、Swift、モバイルの各バンドルは、スキルを 1 つも読まずにステップ 2 で除外されます。`django-patterns` と `django-tdd` は `manage.py:1` と `pytest.ini` を根拠に推奨されます。`django-security` は `settings.py` が環境変数から `DEBUG` を露出しているため推奨されます。`frontend-patterns` は除外され、報告は黙って省くのではなくその旨を書きます。`rules/python/` と `rules/common/` は `pyproject.toml` から導かれます。

**すでに設定済みのリポジトリ。** ステップ 2 では、前回と同じバンドルが 1 つを除いて生き残ります：`.github/workflows/` ディレクトリが消えています。報告はインストール一覧ではなく、削除の推奨から始まります。

**ルックアップの失敗。** `ECC_ROOT` がマニフェストを持たないツリーを指しているため、`install-plan.js` が非ゼロで終了します。ステップ 1 は中断してエラーを報告します。「Recommended (0)」とは報告しません。

## トラブルシューティング

### 「スキルが Claude Code に認識されない」

- スキルディレクトリに `SKILL.md` があることを確認（散在する .md だけではない）
- ユーザーレベル: `~/.claude/skills/<skill-name>/SKILL.md` の存在を確認
- プロジェクトレベル: `.claude/skills/<skill-name>/SKILL.md` の存在を確認

### 「ルールが機能しない」

- レイアウトがインストール方法と一致しているか確認：言語別なら `$TARGET/rules/<language>/`
- ルールのインストール後に Claude Code を再起動

### 「プロジェクトレベルのインストール後にパス参照エラー」

- 一部のスキルは `~/.claude/` パスを前提とします。ステップ 9 がこれらを検出します。
- `continuous-learning-v2` の `~/.claude/homunculus/` は常にユーザーレベルです — 想定どおりであり、エラーではありません。

### ステップ 0 の「Not an ECC tree」

リゾルバが ECC のチェックアウトではないディレクトリを見つけた、ということです — 多くの場合、いま作業しているリポジトリ自身です。`CLAUDE_PLUGIN_ROOT` を設定するか、ECC クローンのパスを渡してください。

### 「期待していたスキルが推奨されなかった」

まず除外の表を確認してください。そのバンドルがステップ 2 で除外されていた場合、そのスキルは個別に評価されておらず、反論すべき相手はバンドルレベルの証拠です。明示的に要求すればインストールされますが、推奨がなかったこと自体が 1 つの所見です。
